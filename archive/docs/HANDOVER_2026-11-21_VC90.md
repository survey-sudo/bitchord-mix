## 3. vc90: what changed and why

### The problem was broader than a classic Echo bypass

Earlier `MusicalHandoff.QUALIFIED` meant safe geometry, full vocal-mask coverage, no certain-lyric amputation, and no prohibited dual-vocal overlap. It **did not establish musical fit**: a BPM-only constant grid and bare effective-end cut could pass even without measured pulse/phrase support.

Historical sample of 45 fires had 11 native Echo, 16 Beat blends, 5 Crown Loops, and 13 classic transitions; all 13 classic transitions had FX NONE. Thus simply blocking classic Echo would not address those native Echo selections. No new Echo recording was supplied; the earlier Loop recording cannot be relabeled as proof of a specific audible Echo defect.

### Production implementation

All paths below are relative to current `src/`.

**A. New positive musical evidence gate**
`shared/src/commonMain/kotlin/com/music/bitchord/playback/smart/EchoAdmission.kt`:

- `musicalRefusal(handoff, out, inn): String?`; null means the added musical-evidence checks passed, not universal safety or listening approval.
- Requires outgoing `tailBeats` and incoming `headBeats`, confidence at least `MIN_BEATMATCH_CONFIDENCE` (0.55), finite BPM > 1, and at least four finite/nonnegative/strictly increasing beats. Reject duplicates, NaN, and reordered beats.
- Checks actual local windows: source minus two beats through end plus four beats, at least four local beats, coverage with at most one expected-beat slack.
- Local median pulse within 12% of side BPM; gaps within 20% of local median; global/local tempo agreement within 12%.
- Outgoing dry end must be near a measured phrase boundary, mix-out candidate/time, or measured tail downbeat (tolerance `min(0.12 s, 0.2 beat)`).
- Incoming audible/landing anchor requires a measured downbeat or declared pickup/audible entry with actual beat coverage.
- Clean vocal masks or a global BPM alone no longer authorize Echo.

- `MusicalHandoff.kt` safety implementation is unchanged. These are additional refusals, not weakened safety.

### Root cause and the correction

The normal incoming decoder follows a **linear rate-1 final-join timeline**, deliberately distinct from the looping native deck's wrapped physical source position. `incomingStartFor` deferred a negative source start only when `hold > 0`. For an unheld Crown it started at mix 0.5 s/source 0 even though its target source time was about −19 s. Alignment could repay that debt by inserting silence. `writeSilence` grows `delegateOffsetUs`; player position subtracts that offset, and Media3 clamps backward reports. Thus the presented position can freeze despite output advancement, triggering the real watchdog.

Recorded geometry: `elementAt=40.230490177`, `handoverTrack=20.3575`; old start 0.5/source 0/debt 19.372990177 s; corrected start 19.872990177/source 0, same final join and >20 s runway. Existing deferred-adoption support handles a start later than nominal handoff.

Only production condition changed:

```diff
- if (hold > 1e-9 && tBase < 0.0 && handoverTrack >= 2.5)
+ if (tBase < 0.0 && handoverTrack >= 2.5)
```

Preserve `handoverTrack >= 2.5`, clamps, linear target, timing guards and the 10 s watchdog. Small handovers below 2.5 s retain prior behavior; this is a bounded fix, not a universal scheduling redesign.

**Explicitly rejected/withdrawn:**

- Raising watchdog timeout to 60 s or disabling it would mask the debt and genuine stalls.
- Replacing linear `handoverTrack + (m - elementAt)` with `clock.inTrackTimeAt(m)` would chase native loop wraps and break the final join. A short replay that stopped before the first wrap misleadingly appeared to converge; it is not a valid fix.
- Treating pure silent-buffer muting as the stall: muting alone still advances source transport. Offset/insertion behavior matters.
- `DELEGATE_FULLY_CONSUMED`, `mix.complete`, or `mix.verify` are not proof of continuous audible AudioTrack presentation.

## 7. Why the APK went from ~87 MB to ~67 MB

This was investigated against the actual saved **87,498,355-byte ARM64 reference**:
`/home/hfzhkn/Storage/Downloads/app-prod-arm64-v8a-release.apk`.
Not the separate 195,329,652-byte four-ABI universal upstream APK with embedded Wear payload.

Both the 87.50 MB reference and current artifact are ARM64-only with the same 14 native filenames, and neither has embedded Wear APK. Models are byte-identical. The dominant difference is **ZIP compression of native libraries**, not model/feature removal:

- Reference native ZIP payload: 36,287,104 bytes, stored uncompressed.
- Current native compressed ZIP payload: about 16,098,613 bytes; raw libraries about 41,887,960 bytes.
- Roughly 20.19 MB saved in native ZIP storage, offset by ~0.28 MB other growth. vc90 is only 4096 bytes larger than vc89.
