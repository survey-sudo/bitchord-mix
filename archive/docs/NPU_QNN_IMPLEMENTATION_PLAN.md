## 1. Failure analysis

BitChord has **two independent, sequentially-proven QNN blockers**. Fixing one does not fix the other. This is the correct mental model; every prior attempt that conflated them wasted device cycles.

### Failure 1 — ORT reduced-build kernel gap (proven to break CPU *and* QNN)

**Evidence** (`evidence/bitchord-device-evidence/vc70-device/on-device-analysis-diagnosis.md:27-48`, `npufix2-logcat-filtered.txt:8`, `exp-search-cpu-fail-quotes.txt`):

```
OrtException: Failed to find kernel for com.microsoft.MatMulIntegerToFloat(1)
  (node:'/m/frontend/blocks/blocks.0/partial/attnF/to_qkv/MatMul_quant' ep:'CPUExecutionProvider')
OrtException: Failed to find kernel for com.microsoft.DynamicQuantizeMatMul(1)
  (node:'/fc1/MatMul_quant' ep:'CPUExecutionProvider')
```

Both EPs die with the same missing kernel in the same binary. Stack frames prove the CPU path (`NpuSession.openCpu` → `BeatTracker.track:141` → `TrackAnalyzer.analyze:1254`), not just the self-test. This is why all ONNX analysis has been dead since vc69: the bundled `libonnxruntime.so` is a **reduced-ops build** whose `ops.config` was generated by `tools/python/create_reduced_build_config.py` from the **raw** `.onnx` graphs. The script is a pure protobuf parse — `_process_onnx_model` does `onnx.load(model_path)` and `_extract_ops_from_onnx_graph` walks `graph.node` (`onnxruntime/tools/python/create_reduced_build_config.py`, main branch) — with no optimizer pass at all.

At session-creation time, ORT's QDQ/graph optimizer (`GraphOptimizationLevel.ORT_ENABLE_ALL`, explicitly used by both `openQnn` and `openCpu` in `NpuSession.kt`) rewrites `DynamicQuantizeLinear` + `MatMulInteger` pairs into `MatMulIntegerToFloat` (beat) and `DynamicQuantizeMatMul` (vocal). Raw-graph binary grep confirms the gap: beat has 62× `MatMulInteger` + 50× `DynamicQuantizeLinear` and **0×** `MatMulIntegerToFloat`; vocal has 3× `MatMulInteger` + 3× `DynamicQuantizeLinear` and **0×** `ToFloat` (`on-device-analysis-diagnosis.md:47-48`). The reduced build therefore lacks the kernels for ops that only exist **after** optimization.

**Partial-fix trap:** session creation reports only the *first* missing kernel. Adding the two known ops by hand may reveal further optimizer-introduced ops after each rebuild. The robust fix regenerates the config from the optimized graph (§2.1).

**Current workaround (in place now):** the full Maven ORT AAR (1.31.0) ships instead of the reduced build, so CPU analysis works. `QNN_ENABLED = false` in `NpuSupport.kt`, QAIRT libs are no longer packaged in the APK, but `npu-addon/prebuilt/jniLibs/arm64-v8a/` still holds them on the builder (V73+V75 Skels, `libQnnHtp.so`, `libQnnSystem.so`, `libQnnHtpPrepare.so`).

### Failure 2 — QNN device-config rejection (independent of Failure 1)

**Evidence** (`npufix2-qnn-grep.txt:6-10`, `on-device-analysis-diagnosis.md:52-64`):

```
[W:onnxruntime:ort-java, qnn_backend_manager.cc:489 QNNExecutionProvider] File mapped weights feature is only available on Windows arm64 …
[W:onnxruntime:ort-java, qnn_backend_manager.cc:308 operator()] Using existing ADSP_LIBRARY_PATH setting of /data/app/~~…/lib/arm64;/vendor/lib/rfsa/adsp;/vendor/dsp/cdsp;/vendor/dsp, which may cause the HTP backend to fail.
[W:onnxruntime:ort-java, qnn_backend_manager.cc:1680 SetupBackend] Failed to setup so cleaning up
[E:onnxruntime:, qnn_execution_provider.cc:1063 GetCapability] QNN SetupBackend failed Failed to create device. Error: QNN_DEVICE_ERROR_INVALID_CONFIG: Invalid config values
```

This fires at `GetCapability` / device-create, **before** graph partitioning and before the missing-kernel lookup. The missing kernel cannot be its cause. It occurred 17× in one production capture (`on-device-analysis-diagnosis.md:54`) and 1× in the self-test. In the production capture there was **no** `ADSP_LIBRARY_PATH` warning, so "BitChord set ADSP_LIBRARY_PATH" alone does not explain every occurrence — the warning and the error co-occurred in the self-test but not identically in production. Root cause remains open (§3).

**What `INVALID_CONFIG` actually is.** `QNN_DEVICE_ERROR_INVALID_CONFIG = 14000 + 1` (QAIRT SDK `include/QNN/QnnDevice.h`; also reported numerically as error `14001` in ORT issue [#21214](https://github.com/microsoft/onnxruntime/issues/21214): "Failed to create device. Error: 14001"). Qualcomm's API docs describe it as "one or more configuration values is invalid" for `QnnDevice_create` / `QnnHtpDevice_create`. ORT surfaces it verbatim from `QnnBackendManager::CreateDevice()`:

```cpp
// onnxruntime/core/providers/qnn/builder/qnn_backend_manager.cc  CreateDevice()
Qnn_ErrorHandle_t result = qnn_interface_.deviceCreate(log_handle_, device_configs_builder.GetQnnConfigs(), &device_handle_);
if (QNN_SUCCESS != result) {
  return ORT_MAKE_STATUS(ONNXRUNTIME, FAIL, "Failed to create device. Error: ", QnnErrorHandleToString(result));
}
```

Critical structural fact: `CreateDevice()` only pushes a `SOC` custom config when `soc_model_ != QNN_SOC_MODEL_UNKNOWN`, and only pushes an `ARCH` custom config when `htp_arch_ != QNN_HTP_DEVICE_ARCH_NONE`. BitChord sets **neither**. ORT therefore calls `deviceCreate` with an **empty config list** (just `QNN_DEVICE_CONFIG_INIT`). An empty list is a documented-valid default (backend autodetects the chip). That means `INVALID_CONFIG` with BitChord's current options **cannot** be caused by a mis-set `soc_model`/`htp_arch` value — no such value is being passed — and the `htp_performance_mode` / `htp_graph_finalization_optimization_mode` / `ep.context_*` options are graph/context configs applied *after* device creation, not device configs at all (verified in `qnn_execution_provider.cc:104-182`: `ParseHtpPerformanceMode` / `ParseHtpGraphFinalizationOptimizationMode` feed graph finalization, a much later stage). The trigger must therefore be **environmental**: something the backend needs in order to reach the DSP (linker visibility, on-disk skel visibility, skel/arch availability) is missing, and the backend reports the resulting failure as the generic `INVALID_CONFIG` bucket. This reframing drives the ranked list in §3.6.

**Precedent for exactly this misdiagnosis.** ORT issue [#31353](https://github.com/microsoft/onnxruntime/issues/31353) ("QNN HTP backend fails with `QNN_DEVICE_ERROR_INVALID_CONFIG` on Snapdragon 8 Elite regardless of `soc_model`/`htp_arch` value") tested every combination of `htp_arch` / `soc_model` / fp16 on SM8750 and got byte-identical `INVALID_CONFIG` every time, with `GetCapability` returning zero nodes and silent full CPU fallback. Resolution (per comments by `Coax1337` and `itsallgoody` on that issue, both later confirmed by the reporter closing the issue as solved): the failure was **not** provider options at all. It was (1) a missing AndroidManifest `<uses-native-library>` declaration for `libcdsprpc.so`, (2) `ADSP_LIBRARY_PATH` handling, (3) `useLegacyPackaging = true` so FastRPC can `fopen()` the skel file on disk, and (4) QAIRT version pairing. The FastRPC `/dev/fastrpc-cdsp` permission bits (`crw-rw-r--`, other=read-only) were investigated and ruled **out** as a barrier — an ordinary sideloaded app reaches the HTP once those four are in place. BitChord is in the same structural position as the #31353 reporter; the same four fixes are the starting point (§3.6).

## 2. Recommendation A — ORT build strategy (Failure 1)

### 2.1 How to capture optimizer-introduced ops

ORT provides exactly one supported, optimizer-aware path. It is **not** `create_reduced_build_config.py` on raw `.onnx`.

**The script's own documentation** (`https://onnxruntime.ai/docs/reference/operators/reduced-operator-config-file.html`):

> "The configuration file can be manually edited as needed. The configuration can be created from either ONNX or ORT format models."
> `create_reduced_build_config.py --help`: `-f {ONNX,ORT}, --format … (default: ONNX)`, `-t, --enable_type_reduction … Only possible with ORT format models.`

With `-f ONNX` it walks raw protobuf nodes (see §1). With `-f ORT` it calls `create_config_from_models` in `util.ort_format_model`, which parses the **ORT flatbuffers** model — and ORT-format models are *optimized graphs* (see below). So `-f ORT` is optimizer-aware **iff** the `.ort` files were produced by an optimizer.

**The optimizer-aware producer** is `convert_onnx_models_to_ort` (`tools/python/convert_onnx_models_to_ort.py`, a stub that calls `util.convert_onnx_models_to_ort`). Its core (`util/convert_onnx_models_to_ort.py`, `_convert`):

```python
so = ort.SessionOptions()
so.optimized_model_filepath = str(output_model_path)
so.graph_optimization_level = optimization_level   # default resolves to ORT_ENABLE_ALL
...
so.add_session_config_entry("session.save_model_format", "ORT")
_ = ort.InferenceSession(str(model), sess_options=so, providers=["CPUExecutionProvider"], …)
```

It literally creates an `InferenceSession` with optimization enabled and `session.save_model_format = "ORT"`, so the saved `.ort` contains the **optimizer-transformed** graph — including `MatMulIntegerToFloat` and `DynamicQuantizeMatMul`. The ORT-format docs confirm this is the intended flow: "Loads and optimizes ONNX format models, and saves them in ORT format" and "Determines the operators … required by the **optimized** models, and saves these in a configuration file" (`https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-models.html`). The conversion script also emits the config directly (`required_operators.config` / `required_operators_and_types.config`).

**Concrete host-only procedure (no device needed):**

```bash
pip install onnxruntime==1.31.0 flatbuffers onnx
# 1. Convert both models (beat + vocal) to ORT format; this runs the optimizer.
python -m onnxruntime.tools.convert_onnx_models_to_ort \
    --optimization_style Fixed --target_platform arm \
    --enable_type_reduction --save_optimized_onnx_model \
    <dir-with-beat_this_final0_q8.onnx+vocals_umxhq_int8.onnx>
# 2. The script writes required_operators_and_types.config from the OPTIMIZED graphs.
#    (Equivalent manual path:)
python tools/python/create_reduced_build_config.py -f ORT -t <dir-with-.ort> ops.config
# 3. Grep-verify the two known ops are now present:
grep -o "MatMulIntegerToFloat\|DynamicQuantizeMatMul" ops.config
```

Equivalently, one can run a model through `onnxruntime.InferenceSession` with `graph_optimization_level = ORT_ENABLE_ALL` and `optimized_model_filepath` set, then run `create_reduced_build_config.py -f ORT` on the emitted `.ort`/`.optimized.onnx`. What does **not** work: `create_reduced_build_config.py -f ONNX` on the raw `.onnx` (that is the bug), hand-adding the two ops (iterates, see §1), or `onnxruntime.tools.offline_tools` / `optimize_onnx_model.py` as a config source — those optimize for *offline transform* purposes and are not the reduced-build config pipeline; the documented pairing is `convert_onnx_models_to_ort` → `required_operators*.config` → `--include_ops_by_config` (build flag confirmed at `tools/ci_build/build_args.py:551-558`).

### 2.2 The four options

| Option | What it is | `libonnxruntime.so` (arm64, uncompressed) | Effort | Risk |
|---|---|---|---|---|
| **(a) Optimizer-aware `ops.config` regen** | `convert_onnx_models_to_ort` → config from optimized `.ort` → rebuild with `--include_ops_by_config ops.config` | ~13 MB (today's reduced size) + a few % for the extra ops. Older official mobile numbers show the same shape: `onnxruntime-mobile` arm64 `.so` 3.96 MB vs full 16.28 MB uncompressed (`https://onnxruntime.ai/docs/tutorials/mobile`, 1.18-era table); current 1.31 sizes are larger but the ratio holds. | Hours of host work + one ORT rebuild (hours) + APK rebuild | Must be re-run on **every** model change; a single forgotten regen re-breaks all analysis silently. Moderate-long-term fragility. |
| **(b) Disable the QDQ optimizer** (`ORT_DISABLE_ALL` / `session.disable_optimizer`) | Session creates without introducing `MatMulIntegerToFloat` / `DynamicQuantizeMatMul` | Same as (a), ~13 MB | Minutes | **Not recommended except as a diagnostic.** Loses all graph fusion/perf opts, not just QDQ; accuracy/perf impact unmeasured and plausibly nonzero (the QDQ optimizer exists to make quantized models CPU-executable efficiently). Also does not help QNN: HTP only supports quantized QDQ models anyway, so disabling the CPU QDQ rewrite does not change what HTP sees — and may change numerics. See §2.3. |
| **(c) Full kernel set** | Omit `--include_ops_by_config` entirely. There is **no** `--include_all_operators` flag in `build_args.py` (checked: only `--include_ops_by_config` and `--enable_reduced_operator_type_support` exist); "all operators" is simply the default when the config flag is absent. `is_reduced_ops_build(args)` is literally `args.include_ops_by_config is not None` (`tools/ci_build/build.py:82-83`). | ~33 MB (gradle-cache-extracted arm64 size in `on-device-analysis-diagnosis.md:157`) | **Zero.** This is the current Maven AAR; analysis already works on it. | None. This is the known-good state. |
| **(d) `--enable_reduced_operator_type_support` off** | Flag only has meaning *with* `--include_ops_by_config` ("Further reduce size by limiting operator data types based on `--include_ops_by_config` file", `build_args.py:556-558`). Turning it off while still passing a config yields plain (a); turning it off with no config is (c). | Same as (a) or (c) depending on config presence | Zero (no-op) | N/A — not an independent option. |

### 2.3 Recommendation

**Adopt (c) full ORT for the target build. Do not ship a reduced build at all.**

Rationale, quantified:

- **Size saving is small in product terms.** Reduced saves ~20 MB uncompressed (33 − 13). The vc70 APK is already 108 MB (vc69: 87.5 MB), and the two models alone are 32.2 MB (`beat_this_final0_q8.onnx` 23,138,816 B + `vocals_umxhq_int8.onnx` 9,054,206 B, per `docs/BITCHORD_HANDOVER_DJMIX25.md:13`). 20 MB is ~19 % of a 108 MB APK — noticeable, but it is not what makes this app feel large, and it already proved it can take down *all* analysis (CPU and NPU) since vc69. A 20 MB premium for a known-good runtime is the correct trade for a music app whose core feature is analysis.
- **The failure cost is total and silent.** The reduced build did not degrade quality; it removed the beat model and the vocal model entirely, with the only symptoms being "no grid" / `NEUTRAL_VOCAL` fallbacks and a cache that silently mixes model-era and DSP-era entries with no provenance (`on-device-analysis-diagnosis.md:66-80`). No user-visible error. That failure mode must be structurally impossible (§5.2), which is easiest by not building reduced at all.
- **(a) is a maintenance trap.** Every model update (re-quantized beat, new umxhq, any asset swap) now requires a regen step that nothing enforces. The regeneration itself is scriptable as a CI gate (`grep MatMulIntegerToFloat`), but the ongoing burden buys only the 20 MB.
- **(b) is a numerics risk.** `ORT_DISABLE_ALL` would have to be validated for Beat This / umxhq accuracy deltas on host before being considered; there is no evidence it is accuracy-neutral, and the QDQ rewrite is load-bearing for CPU execution of these quantized models. Use it only as a one-off diagnostic on host (does the session open with the reduced binary if optimization is disabled? — that would confirm the optimizer is the introducer, which the raw-graph grep already proves).
- **For the QNN add-on (§5), also use full.** Once QAIRT libs (`libQnnHtp.so`, `libQnnSystem.so`, `libQnnHtpPrepare.so`, Stub/Skel) are in the add-on, the add-on's size is dominated by QAIRT, and the 20 MB ORT saving is a smaller fraction still. Full ORT in the add-on removes a second failure surface (config regen) from the harder path.

**Exception:** if a future hard APK-size ceiling (e.g. Play 150 MB cap with more assets) makes 20 MB product-blocking, revisit (a) with the §2.1 procedure plus a CI assertion that the generated config contains the optimizer-introduced ops. Do not revisit it for its own sake.

## 3. Recommendation B — `QNN_DEVICE_ERROR_INVALID_CONFIG` (Failure 2)

### 3.1 What BitChord passes today, option by option

| Option | Value | Valid for ORT 1.31 / QAIRT 2.51? | Can it cause `INVALID_CONFIG` at `deviceCreate`? |
|---|---|---|---|
| `backend_path` | `<libDir>/libQnnHtp.so` (absolute) | Yes — documented as "path to `libQnnHtp.so` … allows one to specify an arbitrary path" (`https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html`). ORT dlopens it directly in `LoadBackend()` and derives `libQnnSystem.so` from its directory in `LoadQnnSystemLib()`. Absolute is *better* than the docs' bare `"libQnnHtp.so"` example, because it removes `LD_LIBRARY_PATH` resolution from the equation. | No — if this were wrong, `LoadBackend` would fail with "Unable to load backend", not reach `deviceCreate`. |
| `htp_performance_mode` | `burst` | Yes — one of the documented modes (`burst, balanced, default, high_performance, high_power_saver, low_balanced, low_power_saver, power_saver, sustained_high_performance`). Parsed in `qnn_execution_provider.cc:104`. | No — graph/context config, applied after device creation. |
| `htp_graph_finalization_optimization_mode` | `3` | Yes — documented `0` (default) / `1` / `2` / `3` ("longest preparation time, most likely even more optimal graph"). Parsed at `qnn_execution_provider.cc:150`. | No — same as above. Orchard used the identical value successfully on SM7450 (§3.3). |
| `ep.context_enable` | `1` | Yes — documented QNN context-binary cache feature. | No — session option processed after `GetCapability`/device-create. |
| `ep.context_file_path` | `<cache>/ctx.onnx` | Yes — documented counterpart of the above. | No — same. (A *stale/corrupt* ctx from a previous reduced-build compile could cause a *later, different* context-load error; it cannot cause `deviceCreate` to fail. Clear `<cache>/ctx.onnx` during diagnosis to remove the variable.) |
| `ep.context_embed_mode` | `1` | Yes — documented: "the content of the context binary is embedded inside the Onnx model." | No — same. |
| `session.disable_cpu_ep_fallback` | `0` | Valid. | No — but see §5.3: for *diagnosis* it should be `1` in the self-test, so a CPU-bound graph throws instead of silently falling back (the exact tripwire recommended in ORT issue #31353). This is a test-harness change, not a fix. |
| `soc_model` / `htp_arch` | **unset** (both) | Valid default. `CreateDevice()` pushes neither config; `deviceCreate` gets an empty list. | No — nothing to be invalid. Adding *wrong* values would be the only way these could cause `INVALID_CONFIG` (see §3.4). |

**Conclusion of the audit:** no BitChord provider option is a plausible `INVALID_CONFIG` trigger at device creation. All QAIRT-visible device configs are unset, and all set options apply downstream of device creation. The failure is environmental. That is consistent with §1's reframing and with issue #31353's finding that *no* combination of options changed the error.

### 3.2 The `ADSP_LIBRARY_PATH` warning — what ORT actually does

ORT source (`onnxruntime/core/providers/qnn/builder/qnn_backend_manager.cc`, `LoadBackend()`):

```cpp
#if defined(__aarch64__) && defined(__linux__)
  // QNN requires ADSP_LIBRARY_PATH to be set in order to find skel libs on Linux
  static std::once_flag set_adsp_path_once;
  std::call_once(set_adsp_path_once, []() {
    constexpr std::string_view kAdspLibraryPathEnvVar{"ADSP_LIBRARY_PATH"};
    const char* existing_path = getenv(kAdspLibraryPathEnvVar.data());
    if (existing_path != nullptr) {
      LOGS_DEFAULT(WARNING) << "Using existing ADSP_LIBRARY_PATH setting of " << existing_path
                            << ", which may cause the HTP backend to fail.";
      return;
    }
    std::filesystem::path qnn_lib_path(GetDefaultEnv().GetRuntimePath());
    LOGS_DEFAULT(INFO) << "Setting " << kAdspLibraryPathEnvVar << " = " << qnn_lib_path;
    setenv(kAdspLibraryPathEnvVar.data(), qnn_lib_path.c_str(), 1);
  });
#endif
```

Semantics:

1. The `once_flag` means ORT sets it **at most once per process**, and **only if nobody else set it first**. The warning fires for *any* pre-existing value — it is a generic "you took responsibility" notice, not a diagnosis that the value is wrong.
2. If BitChord does not set it, ORT sets it to `GetDefaultEnv().GetRuntimePath()` — the runtime's own directory, i.e. the directory containing `libQnnHtp.so` (the bundled lib dir, since `backend_path` points there). That single directory contains the Skels in BitChord's packaging, so ORT's default would be sufficient on its own.
3. BitChord's current value is `<bundled lib dir>;/vendor/lib/rfsa/adsp;/vendor/dsp/cdsp;/vendor/dsp` (semicolon-separated, matching the convention used in issue #31353's reproduction). The bundled dir is first, which is the correct order (bundled Skel wins over vendor firmware). Redundant vendor dirs are harmless *if* the bundled dir is present and first.

**Should BitChord stop setting it? Yes — but as a diagnostic, not as a presumed fix.** Reasons: (i) it removes ORT's warning ambiguity and proves the ORT-default path; (ii) it eliminates the class of "BitChord's path is subtly wrong (separator, missing dir, stale dir from a prior install)" bugs; (iii) it costs one line. Counterpoint: Orchard *does* set it and reportedly worked (§3.3), so setting it is not inherently fatal. The honest statement is: BitChord's value looks correct, and the warning alone does not explain production occurrences without the warning — but "let ORT set it" is the cheapest experiment that either confirms the value (error persists with ORT's own path → ADSP ruled out) or refutes it (error vanishes → BitChord's value was the problem). See ranked fix #2.

What ORT expects: `backend_path` only. `ADSP_LIBRARY_PATH` is not an ORT provider option; it is a plain environment variable that ORT manages as a courtesy. There is no "both required" configuration.

**Bottom line of the diff:** on provider options, BitChord and Orchard are **identical** except `disable_cpu_ep_fallback`. There is no provider-option difference that explains BitChord `INVALID_CONFIG` vs Orchard reportedly working on SM7450. The differences that matter are in **packaging and manifest**: Orchard ships one Skel per add-on APK, dlopens an isolated runtime, and (per its `NpuDevice.kt:55-57` gate) checks `/vendor/lib64/libcdsprpc.so` exists before even attempting — though that file-existence check is *not* the same as the Android 12+ linker-namespace declaration (§3.6 rank 1). Note also the caveat in `ORCHARD_AUTOMIX_ANALYSIS.md:267`: "Historical experiment: production now uses dynamic INT8 ONNX Runtime on CPU. QNN dependencies now removed; NPU results describe earlier experimental build." Orchard itself stopped shipping this path for playback. That does not make BitChord's attempt wrong, but it does mean "Orchard worked" is weaker evidence than it sounds — see §6.

### 3.4 `htp_arch` / `soc_model` for SM8635 — needed or harmful?

**Correct values, if ever set:**

- `htp_arch = 73` for SM8635 (Poco F6). Orchard's map places SM8635 in the v73 bucket (`ORCHARD_AUTOMIX_ANALYSIS.md:239`), and ExecuTorch's canonical table agrees: `SM8635 = 68 # v73`, alongside `SM8550 = 43 # v73`, `SM8650 = 57 # v75`, `SM8750 = 69 # v79`, `SM8850 = 87 # v81`, `SM8350 = 30 # v68` (`pytorch/executorch/backends/qualcomm/serialization/qc_schema.py`). `73` is in ORT's accepted parser set (`68,69,73,75,81` — `ParseHtpArchitecture`, `qnn_execution_provider.cc:168-182`; note: **79 is not in this release's enum**, which is why v79 devices needed PR #31638).
- `soc_model = 68` for SM8635 — **not** `8635`. The provider option takes the QNN `Qnn_SocModel_t` enum number, not the SM string. Passing `8635`, or `60` (the docs' example value for a different chip), or `43` (SM8550) would be an invalid/wrong SoC and *could* produce `INVALID_CONFIG` where unset produces none. The ORT docs' example `"soc_model": "60"` is for whatever chip 60 denotes, not a generic recommendation.

**Recommendation: set neither.** Autodetect (empty device config) is the documented default and matches both Orchard and the ORT docs' minimal example (which sets only `backend_path`). Explicit `htp_arch=73` is a legitimate *diagnostic* (rank 4) because BitChord bundles two Skels and the question "which Skel loads?" is otherwise open — but it should be tested only after ranks 1–3, and success criterion is the loaded Skel name, not just disappearance of the error. Do not set `soc_model` — ORT itself warns the `Qnn_SocModel_t` enum is deprecated and "will not be updated in the future" (`CreateDevice()` comment).

**V73 vs V75 hedge:** bundling both is defensible, but the field question ("whether the device would pick V73 or V75 Skel remains undecided", `npufix2-report.md` §3 — no `HTP ARCH` line was emitted because session creation died before graph finalization) must be answered with the log lines in §5.3. If autodetect yields V73 on SM8635 (expected), the V75 Skel is dead weight and future adds should be one-Skel-per-add-on (Orchard pattern).

### 3.5 Ranked candidate fixes for `INVALID_CONFIG` (cheapest first)

Each fix is one rebuild (or fewer — ranks 1–3 are all APK-level, no ORT rebuild) plus the same device log capture. **Stop at the first fix whose confirmation test passes.** Run device log capture with ORT logging at `VERBOSE` for these iterations (per issue #21214's resolution advice: "Change `ORT_LOGGING_LEVEL_ERROR` to `ORT_LOGGING_LEVEL_VERBOSE`. Then … QNN will say it can't find something"), and add `profiling_level` no; VERBOSE is enough. Capture: `adb logcat -d *:S BitChordTrackAnalyzer:I BitChordNPU:I onnxruntime:I QnnDsp:I | grep -i -E "npu|qnn|adsp|skel|cdsp|device|capability"`.

**Rank 1 — Add the `<uses-native-library>` manifest declaration for `libcdsprpc.so`.**
*Why first:* proven root cause for this exact error code on multiple devices (#31353, `Coax1337` comment 2026-09-08: "`libQnnHtpV79Stub.so` dlopens `libcdsprpc.so` … since Android 12, the app also needs to declare it in the manifest or the linker namespace can refuse the load"; Qualcomm's own `ai-hub-apps` sample does it; "nothing in the ORT docs mentions it"). BitChord's manifest state could not be verified from this host without touching `bk-android`, so this is both cheapest and highest-prior. Cost: one manifest edit.
```xml
<uses-native-library android:name="libcdsprpc.so" android:required="false" />
```
(*One* line is sufficient for HTP; the `libOpenCL.so` line in the same comment is for the GPU backend.)
*Confirmation test:* the following **appear** in logcat, and `INVALID_CONFIG` disappears:
```
Successfully opened file …/lib/arm64/libQnnHtpV73Skel.so
remote_handle64_open: … for file:///libQnnHtpV73Skel.so?qnn_2_51_0_skel_handle_invoke
```
*Refutation / absence of fix:* if these lines are absent and instead you see:
```
Failed in loading stub: dlopen failed: library "libcdsprpc.so" not found: needed by …/libQnnHtpV73Stub.so in namespace clns-*
QnnDsp <E> loadRemoteSymbols failed with err 4000 / Failed to load skel, error: 4000
Transport layer setup failed: 14001
```
then the manifest declaration was missing and this fix is confirmed-but-insufficient (proceed to rank 3). If neither set of lines appears at all (no stub-load attempt), rank 1 was already satisfied and is ruled out as the cause.

**Rank 2 — Stop setting `ADSP_LIBRARY_PATH`; let ORT set it.**
*Why second:* one-line removal, directly tests the only BitChord-specific environmental input ORT warns about. Delete the preflight `setenv("ADSP_LIBRARY_PATH", …)`; do not set it anywhere else.
*Confirmation test:* log changes from
```
[W:onnxruntime:ort-java, qnn_backend_manager.cc:308 operator()] Using existing ADSP_LIBRARY_PATH setting of …
```
to
```
[I:onnxruntime:ort-java, qnn_backend_manager.cc:308 …] Setting ADSP_LIBRARY_PATH = <runtime-path>
```
and either `INVALID_CONFIG` disappears (BitChord's value was the problem — restore a single-dir variant if desired) or persists (ADSP ruled out — restore or keep unset, keep unset for simplicity). *Refutation of "the warning explains everything":* production captures already show `INVALID_CONFIG` without the warning, so expect this to rule out rather than fix.

**Rank 3 — Force on-disk extraction: `jniLibs { useLegacyPackaging = true }`.**
*Why third:* also proven in #31353 (`itsallgoody` comment: "Modern AGP loads native libs straight from the compressed APK … FastRPC's loader needs a real file to `fopen()`; it can't read into the APK zip the way the linker can"; also explains "`Coax1337`'s 'worked once, then went back to failing'"). App-side `dlopen` succeeding (`adspReady=true`) does **not** prove the Skel is on disk. Cost: one Gradle line.
*Confirmation test:* before the flag, `adb shell ls -l /data/app/~~…/lib/arm64/libQnnHtpV73Skel.so` shows **no such file** (APK-zip serving) or the DSP never reaches `Successfully opened file …`; after the flag, the file exists on disk and the rank-1 success lines appear. On-device logs already show BitChord can `ls` that dir (`on-device-analysis-diagnosis.md:6-8`) — extend that to list the Skel files explicitly in the next capture.

**Rank 4 — Pin `htp_arch = 73` only (diagnostic for Skel selection).**
*Why fourth:* only needed because BitChord hedges two Skels. Cost: one provider-option line. Do **not** add `soc_model`.
*Confirmation test:* logs show the **V73** Stub/Skel loading (`libQnnHtpV73Skel.so`); if autodetect was loading V75 (wrong on SM8635), pinning changes behaviour and is retained. If logs show V73 under autodetect too, remove the pin. If pinning to 73 *causes* an error, remove it (wrong-arch pin is the one way to *create* invalid config).

**Rank 5 — Audit the packaged file set (Stub, `.cat`, Prepare, System).**
*Why fifth:* requires listing `npu-addon/prebuilt/jniLibs/arm64-v8a/` on the builder (a read the current build worker must not be disturbed for — do it after that build parks) and confirming the *per-generation* completeness Orchard uses: `libQnnHtp.so + libQnnSystem.so + libQnnHtpPrepare.so + libQnnHtp{gen}Stub.so + libQnnHtp{gen}Skel.so` (`build.sh` per `ORCHARD_AUTOMIX_ANALYSIS.md:237`). The task brief lists "V73+V75 Skels, `libQnnHtp.so`, `libQnnSystem.so`, `libQnnHtpPrepare.so`" — **Stubs are not mentioned**. A missing `libQnnHtpV73Stub.so` would fail earlier than `deviceCreate` ("Unable to load backend" class), so this is unlikely to be *the* cause, but completeness must be verified before concluding.
*Confirmation test:* `ls` shows all five files per generation (Skel + Stub for V73 and V75), plus the `.cat` file if QAIRT 2.51 requires it (issue #21214's working file list included `libqnnhtpv73.cat`).

**Rank 6 — Bisect `htp_graph_finalization_optimization_mode` 3 → 0 (diagnostic only) and clear ctx.**
*Why last:* expected to rule out, not fix (these options cannot affect `deviceCreate`, §3.1). Set mode `0`, delete `<cache>/ctx.onnx`, re-run. If `INVALID_CONFIG` persists byte-identically (expected), graph-finalization mode and context are definitively ruled out and no further option-bisection is warranted. If it vanishes, the bug is elsewhere (QAIRT 2.51 + mode-3 + V73 interaction) and should be filed upstream with these logs.

**Explicitly deprioritised (do not chase):** `/dev/fastrpc-cdsp` permission bits (ruled out in #31353; an ordinary sideloaded app reaches HTP once ranks 1–3 are in), FastRPC-before-`GetCapability` op-support theories (the failure is before op evaluation by definition), and `soc_model` guessing.

### 4.1 Orchard's published numbers (the only measured NPU data available)

All Orchard numbers are measured on **Snapdragon 7 Gen 1 (SM7450, razr 2023)** — the only phone used (`ORCHARD_AUTOMIX_ANALYSIS.md:269`). BitChord's target SM8635 is a newer, faster part, so absolute times will differ; ratios are the transferable part.

|---|---|---|---|
| small0 | 210.3 ms | 68.6 ms | 3.06× |
| final0 | 316.0 ms | 79.3 ms | 3.99× |

Cached load: 248.5 / 377.4 ms. First compile: 60.4 / 62.8 s.

**Speed (30 s, final0):** CPU static A8W8 3,721.3 ms vs NPU 1,191 ms median (1,187–1,253, ~25× real-time) → **3.1×**. But compile was 529.7 s into a 54.5 MB context, and "full-size fast-mode >120 s/crash ~3 GB heap". Full-length NPU is not a shipping configuration.

|---|---|---|

| final0 host FP32, 6 s | 84.33 | 62.41 |

### 4.2 Mapping to BitChord's pipeline

BitChord's analysis path (from `docs/BITCHORD_HANDOVER*.md` and `on-device-analysis-diagnosis.md`):

- Models: Beat This `final0` q8 (23.1 MB) for beat grid + umxhq `vocals_umxhq_int8` (9.0 MB) for vocal mask. Both are **dynamic INT8** ONNX, not QDQ A8W8 — see the critical caveat in §4.4.
- `TrackAnalyzer.analyze()` (whole-track) + `analyzeHead()` (head), `BeatTracker.track()`, `VocalTracker.session()`, then native DSP (`libbitchord_analysis.so`) for BPM/downbeats/key/structure regardless of model success.
- Latency gating: `PrepLead` adaptive arm lead **20–35 s** (prep >8 s pushes to the long end), `LOOP_PRIME_LEAD_MS = 40 s`, `blendArmLeadMs` 20–35 s, `DeckBudget` 40 s horizon, cold-loop slow-build yields at 14 s cold / 10 s warm, next + next+1 eager prefetch (post-vc60 gate removal), 2-thread analyzer pool. No on-device BitChord CPU analysis time in seconds is recorded in the docs consulted — do not quote one. The honest estimate must use Orchard's SD7Gen1 proxy (262 ms/window CPU) and be labelled as such.

**Assuming Orchard ratios transfer**, a 3–4× inference speedup converts a head analysis that today takes ~8–10 s (the `PrepLead` threshold) into ~2–3 s. That is the entire benefit case:

### 4.3 What improves, what does not

| Behaviour | Improves? | Mechanism |
|---|---|---|
| **Pre-arm window** | **Yes, marginally.** `PrepLead` adaptive logic keys off prep time (>8 s → 35 s lead). Faster inference keeps more pairs on the short (20 s) lead and reduces `analy­sing…` at mix time (the U6 class: "this song: analysed … next: analysing…" at the transition). | Analysis-ahead headExecutor + next/next+1 queue. |
| **Native capture rate / loop availability** | **Yes, marginally.** Cold-loop `insufficient-cold-lead` yields (23/29 declines pre-vc67 per forensic audit) and `qualityA="none"` starvation (45 plans, 0 fires on the flagship pair) are gated on analysis readiness. Faster analysis converts some cold yields to loop arms. | `primeLoopDecks` ordering, `loopRegion` complete-rendition gate. |
| **Queue lookahead** | **Yes.** Next+1 analysis finishes within the current track's remaining time more often. | Eager prefetch. |
| **Cold-start** | **Yes, but only just.** First analysis after launch still pays context compile (Orchard: ~60 s for 6 s windows) unless a cached context exists (Orchard: 248–377 ms load). BitChord's selftest already compiles/runs once (`selftest done in 2641 ms` — that figure is the *failed* selftest, so a successful compile will be far slower). Cold-start NPU is worse until the context is cached. | `ep.context_embed_mode=1` cache. |
| **Beat accuracy / grid placement** | **No — it degrades.** NPU A8W8 loses 1.2 pp beat / 5.4 pp downbeat F1 at 6 s, catastrophic at 30 s (§4.1). Any grid difference is noise added by the accelerator, not signal. | QDQ quantization for HTP. |
| **Vocal separation quality** | **No.** BitChord's vocal mask comes from umxhq; Orchard's Syvenu/umxhq experience is that the model only feeds planning penalties and filter-depth curves, and "A missing model leaves Earmark's flat filter ride" (`ORCHARD_AUTOMIX_ANALYSIS.md:134`). NPU changes latency, not mask quality. BitChord's Wiener `SeparateVocalWindow` (≤22.8 s) is DSP, untouched by NPU. | — |
| **Key finding, tempo, structure** | **No.** Native DSP (`TrackFeatures.analyze`), unaffected by ONNX EP choice. The 164/90 key-parity errors are a pre-existing keyfinder behaviour (`on-device-analysis-diagnosis.md:103-120`). | — |
| **Rendered audio (filters, stretch, limiter, echo)** | **No.** Render path is Signalsmith/native, never on the audio callback in either design. | — |

### 4.4 The caveat that may dominate all of the above

**The QNN HTP backend only supports quantized models** (`https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html`: "The QNN HTP backend only supports quantized models. Models with 32-bit floating-point activations and weights must first be quantized …"). Orchard therefore shipped a **separate A8W8 asset** for NPU (`models/npu/qnn/nirovi_qnn.onnx` 7.7 MB and `syvenu_qnn.onnx` 709 KB) and kept its CPU asset as dynamic INT8 (`nirovi_int8.ort`). Its docs describe the calibration pipeline (`get_qnn_qdq_config`, MinMax, 203 random non-GTZAN 1500-frame samples, `CalibMaxIntermediateOutputs 8`).

BitChord's current assets (`beat_this_final0_q8.onnx`, `vocals_umxhq_int8.onnx`) are dynamic-INT8 CPU assets. **Whether they dispatch to HTP as-is is unknown and probably not** — they will at best partition partially to CPU, at worst fail op-support validation. Orchard's own production conclusion was: "*Historical experiment: production now uses dynamic INT8 ONNX Runtime on CPU. QNN dependencies now removed; NPU results describe earlier experimental build.*" (`ORCHARD_AUTOMIX_ANALYSIS.md:267`). A BitChord NPU project must therefore budget for producing and validating QDQ assets (host calibration + device accuracy comparison) as a first-class phase, not assume the existing `.onnx` files "just work on NPU". (Per-op HTP support also excludes `Loop`/`If`, dynamic shapes — both models must be shape-fixed for QNN; QNN EP "does not support models with dynamic shapes". BitChord's models are loaded with fixed windows, but this must be verified per asset.)

### 4.5 Realistic expected benefit

**Modest.** Say it plainly: NPU is an optimization to background analysis that already has 20–40 s of lead time on a flagship phone. It converts marginal pairs (streamed tracks, quick queue hops, next+1 lookahead, slower devices, battery-sensitive sessions) from `quality=none`/cold-yield to analysis-ready a few seconds earlier. It does not make any beat more accurate, any vocal cleaner, any transition musically better, or any render faster. The single most valuable NPU outcome would be the *absence* of the U6 "next: analysing…" state at mix time on mid-tier Snapdragon devices.

**Sequencing implication:** restoring CPU analysis correctness (Failure 1, full ORT) strictly dominates NPU work. NPU work after that is P2 optimization behind a selftest gate, never a dependency of analysis correctness. If QDQ assets are needed (§4.4), the accuracy cost of those assets (not just speed) must be measured before shipping them — Orchard's 30 s catastrophe is a warning against long-window QDQ on HTP, not a curiosity.

## 5. Recommendation D — Integration design

### 5.1 Build structure

**Adopt Orchard's add-on separation; do not merge QNN into the main APK.**

Orchard's structure (`ORCHARD_AUTOMIX_ANALYSIS.md:230-244`):

- Main APK: minimal/CPU ORT, no QAIRT. Analysis always works.
- **Six add-on APKs** (one per Hexagon gen), each containing its own `libonnxruntime.so` + `liborchard_qnn.so` shim + `libQnnHtp.so`/`libQnnSystem.so`/`libQnnHtpPrepare.so`/`libQnnHtp{gen}Stub.so`/`libQnnHtp{gen}Skel.so`, zipped, aligned, signed, with `npu-addons.json` manifest.
- Add-on downloaded at runtime only after user consent, signature-checked (`pm.checkSignatures == SIGNATURE_MATCH` + `longVersionCode >= MIN_VERSION_CODE`), SHA256-verified, installed via FileProvider intent.
- `liborchard_qnn.so` dlopens by absolute path so the app's `libonnxruntime.so` never satisfies it. The two runtimes coexist because they are **different files at different paths, loaded by different dlopens** — never two files claiming the same soname location.

For BitChord, concretely:

1. **Main APK** (`cpu` default): full Maven ORT AAR 1.31.0 (already current, already working). No QAIRT, no reduced build, `QNN_ENABLED=false` unless add-on present. Analysis depends only on this APK.
2. **QNN add-on APK** (per-gen, starting with V73 only — SM8635's generation — plus V75 as second): built in `npu-addon/` with `--use_qnn static_lib` ORT **full** build (no `--include_ops_by_config`), QAIRT 2.51 libs, and a small JNI shim (`libbitchord_qnn.so`) exposing `bitchord_qnn_open/run/close` over its own ORT copy, modelled on `liborchard_qnn.so`. The shim loads `libonnxruntime.so` by path; the app never loads the add-on's ORT through the normal `System.loadLibrary("onnxruntime")` path.
3. **Runtime switch** (existing `NpuSupport` shape, kept): detect SoC → offer download (consent dialog with size) → download + verify + install add-on → `nativeSelfTest()` on silence (finite-output check + profiling-trace proof, §5.3) → only then persist `QNN_ENABLED=true` + compile marker. Any failure → stay on CPU. Off-Snapdragon → CPU by design, no prompt.
4. **Runtime loading alternative considered and rejected:** shipping both runtimes in one APK (Gradle `pickFirsts`-style or `productFlavors` producing two APKs) either reintroduces the single-file collision (§5.2) or doubles the delivery surface (two APKs, version skew). Flavors are the fallback if a download server is unavailable: `flavor cpu` (Maven AAR) vs `flavor qnn` (from-source QNN ORT + QAIRT), installed by the user as separate APKs, never merged. The add-on approach is still preferred because the main APK never changes and a QNN experiment can never break the CPU path.

What Orchard did is right for BitChord, with two BitChord-specific adjustments: (i) start with **one** generation (V73) not six — BitChord's proven device is SM8635 and extra generations are untested weight; (ii) use **full** ORT in the add-on (§2.3), not Orchard's minimal build, to avoid re-importing Failure 1 into the harder path.

### 5.2 The guard that makes "broke analysis" structurally impossible

The vc69–vc70 breakage mechanism was `jniLibs { pickFirsts += "**/libonnxruntime.so" }` (`app/build.gradle.kts:241-242` per diagnosis): two `libonnxruntime.so` files (Maven AAR + `npu-addon/prebuilt`) competed for the **same** APK path, and `pickFirsts` silently selected the reduced one, replacing the working CPU runtime globally. The specific guards, all cheap, all CI-enforced:

1. **No `pickFirsts` for any `.so`, ever.** Add a CI grep: `grep -rn "pickFirsts" app/build.gradle.kts` must return empty (or only an allowlisted, commented, non-`onnxruntime` entry with a linked issue). This is the direct regression tripwire for the exact line that caused the outage.
2. **Exactly one `libonnxruntime.so` per APK.** CI step: `unzip -l <apk> | grep -c "lib/.*/libonnxruntime\.so" == 1` for the main APK (expect the Maven AAR's), and for each add-on APK (expect the from-source full build's, at the add-on's own path). Fail the build on any count ≠ 1. The add-on APK and the main APK are separate artifacts; there is no merge step where a second copy could appear.
3. **`.so` inventory in CI.** `unzip -l <apk> | grep "\.so"` recorded per build; a diff that adds/removes any `libonnxruntime*` / `libQnn*` / `libbitchord_qnn*` entry fails without an explicit sign-off line in the PR. This catches a future `npu-addon/prebuilt` drop into the main APK.
4. **No shared global ORT symbol.** The add-on's ORT is only reachable via `dlopen("/data/app/.../lib/libonnxruntime.so")` through the shim's explicit path (Orchard pattern). The app's JVM never `System.loadLibrary`s the add-on copy. Even if both are installed, they cannot alias.
5. **Selftest-gated enablement** (already in `NpuSupport`: silence selftest + finite check + `compiling`/`ready` marker). Persist `QNN_ENABLED=true` only after the §5.3 proof lines appear. A broken add-on leaves the app on CPU, not broken.
6. **CPU-works assertion** (§5.3) run in CI on the main APK (emulator, forced QNN-fail path): analysis completes with the model. The last outage would have failed this on day one.

With (1)+(2), reintroducing the outage requires deliberately disabling all three checks; with (4), it cannot affect the CPU path even if the add-on is corrupt.

### 5.3 Acceptance tests

**QNN-actually-executing proof (all required; opening the EP is not sufficient).** On SM8635, with the add-on installed and `QNN_ENABLED` toggled on, run one analysis pass with VERBOSE ORT logging and assert:

1. Backend loaded (not just dlopened):
```
[I:onnxruntime:ort-java, qnn_backend_manager.cc…] Found valid interface, version: 2.51.x backend provider name: … backend id: 3
```
2. ADSP resolved one way or the other:
```
[I:…] Setting ADSP_LIBRARY_PATH = <runtime-path>          (rank-2 path)
# or
[W:…] Using existing ADSP_LIBRARY_PATH setting of …        (rank-1/3 path; warning alone is not failure)
```
3. Device created (absence of the failure lines is the signal):
```
[I:…] Create device.
(no "[W:… SetupBackend] Failed to setup so cleaning up", no "QNN_DEVICE_ERROR_INVALID_CONFIG")
```
4. Skel loaded — **this names the generation** (settles V73 vs V75):
```
Successfully opened file …/lib/arm64/libQnnHtpV73Skel.so
remote_handle64_open: … for file:///libQnnHtpV73Skel.so?qnn_2_51_0_skel_handle_invoke
```
5. `GetCapability` returned non-empty (silent-empty means full CPU fallback, per #31353 — assert `cpu_layer_count == 0` equivalent; strongest form: run with `session.disable_cpu_ep_fallback=1` in the selftest and require session creation to *succeed* — a CPU-bound graph must throw `ORT_FAIL … "assigned to the default CPU EP, but fallback to CPU EP has been explicitly disabled"` per #31353).
6. Nodes actually ran on QNN (not just claimed): `enableProfiling()` trace of a real `run()` contains `"provider": "QNNExecutionProvider"` / `dur` tagged `QNNExecutionProvider` for the graph, and zero occurrences of `"CPUExecutionProvider"` for the QNN sub-graph. (This is the exact verification method used in #31353.)
7. Inference is finite on silence: `selftest provider=QNN inference=finite` (or BitChord's equivalent), and `selftest done in <ms>` where `<ms>` is the *successful* compile+load time, comparable to Orchard's 248–377 ms cached-load range once the context is cached (first compile will be tens of seconds; record both).
8. BitChord-level: `BitChordTrackAnalyzer: NPU QNN open …` with **no** following `NPU QNN open failed; falling back to CPU` line, and a real track analysis yields a model grid (`grid=model`, not `grid=dsp` fallback) with wall time ~3–4× faster than the CPU baseline on the same track (record both numbers; do not claim a ratio you did not measure).

**CPU fallback assertion (required; this is the "never broke analysis again" proof):** with the add-on **uninstalled** (and with a deliberately corrupt add-on in a second run), assert: `NPU QNN open failed; falling back to CPU` → `NpuSession.openCpu` succeeds → **no** `Failed to find kernel` → **no** `Beat model unavailable` → analysis completes and `AnalysisStore` persists the result. Plus: `QNN_ENABLED=false` + no add-on = byte-identical analysis behaviour to today (full Maven AAR). This assertion, not the QNN proof, is the release gate for the main APK.

## 7. What is still unknown (requires on-device iteration)

Stated explicitly so the executing worker does not treat any of the following as settled:

1. **Root cause of `INVALID_CONFIG` on SM8635.** §3.5 ranks are hypotheses ordered by external precedent (#31353, #21214), not by BitChord-specific proof. No BitChord VERBOSE QNN log at `deviceCreate` exists in the evidence consulted. The manifest state of BitChord (does it declare `libcdsprpc.so`?) and its Gradle `jniLibs` legacy-packaging state could not be verified from this host (reading them would require the `bk-android` tree, which is off-limits to this worker). Ranks 1 and 3 are therefore the first two things to check *by reading the files*, before any rebuild.
2. **Whether the packaged file set is complete per generation** — specifically whether `libQnnHtpV73Stub.so` / `libQnnHtpV75Stub.so` (and any `.cat` file) are in `npu-addon/prebuilt/jniLibs/arm64-v8a/`. The brief lists Skels + Htp + System + Prepare; Stubs are unconfirmed. Verifiable by `ls` once the build worker parks; not verifiable now.
3. **Which Skel the DSP loads on SM8635** (V73 expected, V75 hedge). No `HTP ARCH` / skel-load line exists in evidence because creation died first. Answered by §5.3 #4.
4. **QAIRT 2.51.0 vs Poco F6 DSP firmware compatibility.** Bundled QAIRT version is known; device firmware version and its expected skel `_modver` / `qnn_2_51_0_skel_handle` pairing are not. A mismatch surfaces as error 5000 (incompatible binaries), not 14001, per #31353 — so the current error code argues against pure version mismatch, but this is inference, not proof.
5. **Full missing-op set.** Only two optimizer-introduced ops are confirmed (`MatMulIntegerToFloat`, `DynamicQuantizeMatMul`). Phase 0's regen answers whether more exist. Under the §2.3 full-build recommendation this is informational, not blocking.
6. **Whether BitChord's dynamic-INT8 assets dispatch to HTP at all** without QDQ conversion (§4.4). This is the largest open risk to the benefit case and cannot be resolved by reasoning — it needs the phase-3 audit and a device run.
7. **BitChord-local CPU and NPU timings.** No BitChord wall-clock analysis time on SM8635 appears in the docs consulted. All speed numbers herein are Orchard's SM7450 measurements extrapolated by ratio. Phase 5 must measure BitChord's own numbers before any user-facing claim.
8. **Orchard's exact `ADSP_LIBRARY_PATH` value and its current shipping state.** `/tmp/orchard-analysis` is gone from this host; the analysis doc records that Orchard sets the variable but not to what, and records that Orchard production moved to CPU INT8. Orchard is therefore a packaging-pattern reference (§5.1), not a provider-option oracle.
9. **Whether the production-required `cache/ctx.onnx` interferes once QNN opens.** Context was never successfully created on this device. Stale-context handling must be validated in phase 4; clear it during all bisection runs.
